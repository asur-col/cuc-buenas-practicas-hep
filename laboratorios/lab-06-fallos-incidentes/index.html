El incidente

Los de Ventas (pc1, LAN 10.50.1.0/24) reportan que no alcanzan el servidor srv1 (LAN 10.50.4.0/24). La red tiene dos caminos entre las LANs: por r2 y por r3 — pero algo pasó. Tu trabajo como encargado de red: diagnosticar con evidencia, reparar, dejar el servicio resiliente y escribir el informe del incidente.

                    ┌──── r2 ────┐
   pc1 ── eth0 r1 ──┤            ├── r4 eth0 ── srv1
   (10.50.1.10)     └──── r3 ────┘   (10.50.4.10)

Paso 1 — Diagnostica (recoge la evidencia para tu informe)

netcli r1
r1> enable

r1# show ip route
$ ip netns exec lab-pc1 ping -c1 10.50.4.10
$ ip netns exec lab-pc1 traceroute 10.50.4.10

Anota las salidas: son la sección Evidencia de tu informe.

Paso 2 — Repara el enlace y direcciona

El enlace roto hay que levantarlo con no shutdown y toda la malla hay que direccionarla (r1, r2, r3, r4 con el plan de arriba). Ejemplo de r1:

r1# configure terminal
r1(config)# interface eth0
r1(config-if)# ip address 10.50.1.1 255.255.255.0
r1(config-if)# no shutdown
r1(config-if)# exit
r1(config)# interface eth1
r1(config-if)# no shutdown
r1(config-if)# ip address 10.50.12.1 255.255.255.252
r1(config-if)# exit
r1(config)# interface eth2
r1(config-if)# ip address 10.50.13.1 255.255.255.252
r1(config-if)# no shutdown
r1(config-if)# exit

(Y no olvides los PCs: ip addr add … + ip route add default via ….)

Paso 3 — Rutas con respaldo (lo que evita el próximo incidente)

Ida (en r1, hacia la LAN del servidor): principal por r2, flotante por r3 — el último número es la métrica:

r1(config)# ip route 10.50.4.0 255.255.255.0 10.50.12.2 10
r1(config)# ip route 10.50.4.0 255.255.255.0 10.50.13.2 20

Vuelta (en r4, hacia la LAN de Ventas): principal por r3, flotante por r2:

r4(config)# ip route 10.50.1.0 255.255.255.0 10.50.34.1 10
r4(config)# ip route 10.50.1.0 255.255.255.0 10.50.24.1 20

Y en r2/r3 las rutas de tránsito:

r2(config)# ip route 10.50.1.0 255.255.255.0 10.50.12.1
r2(config)# ip route 10.50.4.0 255.255.255.0 10.50.24.2
r3(config)# ip route 10.50.1.0 255.255.255.0 10.50.13.1
r3(config)# ip route 10.50.4.0 255.255.255.0 10.50.34.2

Por qué asimétrico: con rutas estáticas, si la ida y la vuelta prefirieran el mismo camino y este cayera en su tramo inicial, la vuelta seguiría intentando por un router que ya no sabe cruzar. Repartir los caminos principales (ida por r2, vuelta por r3) hace que la caída de r1–r2 solo fuerce a la ida a conmutar, y la vuelta ya iba por r3.

Paso 4 — Verifica y documenta

[pc1] $ ping -c1 10.50.4.10          # servicio restaurado
r1# show ip route                     # aparecen las dos rutas (métricas)
r4# show ip route

Después escribe /workspace/incidente.md con estas cuatro secciones (el verificador las exige):

  1. Causa raíz — qué pasó realmente (no el síntoma).
  2. Evidencia — comandos y salidas que recogiste en el diagnóstico.
  3. Acciones correctivas — qué hiciste, paso a paso.
  4. Prevención — qué harás para que no se repita.

Paso 5 — El verificador tira la red (a propósito)

Cuando ejecutes revisar, el servidor apagará el enlace r1–r2 para comprobar que tu red sigue viva por el otro camino, y luego lo restaurará. Si solo configuraste un camino, ese criterio se pondrá en rojo: la resiliencia no se declara, se demuestra.
