Lab 6 — Fallos e incidentes: diagnóstico, reparación y redundancia

Asignatura: Buenas Prácticas de Redes de Telecomunicaciones (HEP) · Lab 6 · Tiempo estimado: 90 min · Semana: S6

Objetivo

Red con DOS caminos entre la LAN de pc1 (r1) y la LAN de srv1 (r4). Llega ROTA: el enlace r1–r2 nace apagado (administratively down) y no hay rutas entre las LANs. Debes:

  1. Diagnosticar el estado inicial (interfaces down, sin IPs, sin routing)
  2. Hardening en los 4 routers (r1, r2, r3, r4)
  3. Direccionar todas las interfaces según plan de direccionamiento
  4. Levantar el enlace caído (r1 eth1 / r2 eth0)
  5. Configurar rutas estáticas con redundancia: camino principal (r1→r3→r4) AD=1 y camino flotante (r1→r2→r4) AD=10
  6. Verificar conectividad extremo a extremo y failover automático al caer el principal
  7. Escribir informe de incidente
Guía verificada: ejecutada sobre estación desechable (oco-tmp-lab06-station, imagen labs/hep-redes-lab06:1.0.0). Salidas reales de diagnóstico, configuración 4 routers, rutas principal/flotante, tests de conectividad y failover.

Paso 1 — Diagnóstico inicial: estado de fábrica roto ≈10 min

Verificar que r1 eth1 está administratively down, ningún router tiene IPs ni rutas, Telnet habilitado.

Comando exacto (en cada netcli rX):

enable
show running-config
show ip interface brief

Verificación: r1 eth1 admin down = causa raíz; 4 routers sin IPs, sin routing, Telnet activo.

Verificador: criterio de diagnóstico de incidente.

Paso 2 — Hardening y direccionamiento en r1 ≈15 min

Seguridad + IPs en 3 interfaces + levantar eth1 (enlace a r2).

Comando exacto (en netcli r1):

configure terminal
hostname R1-HEP

Error típico: olvidar no shutdown en eth1 → enlace r1-r2 sigue caído. Corrección: siempre no shutdown tras IP.

Paso 6 — Rutas estáticas con redundancia (principal + flotante) ≈15 min

Configurar rutas en los 4 routers: r1 y r4 con dos rutas (AD=1 principal, AD=10 flotante); r2 y r3 con rutas de retorno.

Comando exacto (en cada router):

# r1: principal via r3 (AD=1), flotante via r2 (AD=10)
ip route 10.50.4.0 255.255.255.0 10.10.13.2
ip route 10.50.4.0 255.255.255.0 10.10.12.2 10

# r2: retorno a pc1 y a srv1
ip route 192.168.1.0 255.255.255.0 10.10.12.1
ip route 10.50.4.0 255.255.255.0 10.10.24.2

# r3: retorno a pc1 y a srv1
ip route 192.168.1.0 255.255.255.0 10.10.13.1
ip route 10.50.4.0 255.255.255.0 10.10.34.2

# r4: principal a pc1 via r2 (AD=1), flotante via r3 (AD=10) + rutas a enlaces intermedios
ip route 192.168.1.0 255.255.255.0 10.10.24.1
ip route 192.168.1.0 255.255.255.0 10.10.34.1 10
ip route 10.10.12.0 255.255.255.252 10.10.24.1
ip route 10.10.13.0 255.255.255.252 10.10.34.1

Salida real (show ip route en r1 y r4):

R1-HEP# show ip route
C  10.10.12.0/30 directamente conectada, eth1
C  10.10.13.0/30 directamente conectada, eth2
O  10.50.4.0/24 via 10.10.13.2, eth2      ! principal (AD=1)
O  10.50.4.0/24 via 10.10.12.2, eth1      ! flotante (AD=10)
C  192.168.1.0/24 directamente conectada, eth0

R4-HEP# show ip route
C  10.10.24.0/30 directamente conectada, eth1
C  10.10.34.0/30 directamente conectada, eth2
C  10.50.4.0/24 directamente conectada, eth0
O  192.168.1.0/24 via 10.10.24.1, eth1    ! principal (AD=1)
O  192.168.1.0/24 via 10.10.34.1, eth2    ! flotante (AD=10)
O  10.10.12.0/30 via 10.10.24.1, eth1
O  10.10.13.0/30 via 10.10.34.1, eth2

Verificación: r1 tiene DOS rutas a 10.50.4.0/24 (principal eth2→r3, flotante eth1→r2); r4 tiene DOS rutas a 192.168.1.0/24 (principal eth1→r2, flotante eth2→r3).

Error típico: rutas sin AD o AD invertido. Corrección: ip route ... 1 para principal, ... 10 para flotante.

Verificador: criterio de redundancia y rutas estáticas.

Paso 7 — Configurar pc1 y srv1 ≈5 min

IPs en sus respectivas LANs con gateway hacia su router.

Comando exacto (desde host de la estación):

# pc1 (LAN r1: 192.168.1.0/24, gw 192.168.1.1)
ip netns exec lab-pc1 ip addr add 192.168.1.10/24 dev eth0
ip netns exec lab-pc1 ip link set eth0 up

ip netns exec lab-srv1 ip addr add 10.50.4.10/24 dev eth0

ip netns exec lab-srv1 ip route add default via 10.50.4.1

Salida real: pc1 192.168.1.10/24 gw 192.168.1.1; srv1 10.50.4.10/24 gw 10.50.4.1.

Verificación: ip netns exec lab-pc1 ip route muestra default via 192.168.1.1.

Verificador: criterio de direccionamiento hosts.

Paso 8 — Verificar conectividad extremo a extremo (camino principal) ≈10 min

Confirmar que pc1 ↔ srv1 funciona por el camino principal r1→r3→r4.

Comando exacto:

ip netns exec lab-pc1 ping -c 2 10.50.4.10
ip netns exec lab-srv1 ping -c 2 192.168.1.10
ip netns exec lab-pc1 timeout 5 bash -c "< /dev/tcp/10.50.4.10/80 && echo OPEN || echo CLOSED"

Salida real:

PING 10.50.4.10 ... 64 bytes from 10.50.4.10: icmp_seq=1 ttl=61 time=0.097 ms
2 packets transmitted, 2 received, 0% packet loss

PING 192.168.1.10 ... 64 bytes from 192.168.1.10: icmp_seq=1 ttl=61 time=0.040 ms
2 packets transmitted, 2 received, 0% packet loss

OPEN

Verificación: 0% pérdida bidireccional; TTL=61 = 3 saltos (pc1→r1→r3→r4→srv1) = camino principal activo; web OPEN.

Error típico: Destination Net Unreachable = faltan rutas estáticas. Corrección: revisar show ip route en los 4 routers.

Verificador: criterio de conectividad y camino principal.

Paso 9 — Probar failover: apagar camino principal y verificar flotante ≈10 min

Simular caída del enlace principal (r1 eth2) y confirmar que el tráfico usa automáticamente el camino flotante r1→r2→r4.

Comando exacto:

# En r1: apagar eth2 (enlace a r3)
netcli r1 enable configure terminal interface eth2 shutdown end

# Verificar que ruta principal desaparece y queda la flotante
netcli r1 show ip route

# Test conectividad tras fallo
ip netns exec lab-pc1 ping -c 2 10.50.4.10
ip netns exec lab-pc1 timeout 5 bash -c "< /dev/tcp/10.50.4.10/80 && echo OPEN || echo CLOSED"

# Restaurar enlace principal
netcli r1 enable configure terminal interface eth2 no shutdown end

Salida real:

R1-HEP# show ip route (tras shutdown eth2)
C  10.10.12.0/30 directamente conectada, eth1
O  10.50.4.0/24 via 10.10.12.2, eth1      ! SOLO ruta flotante queda
C  192.168.1.0/24 directamente conectada, eth0

PING 10.50.4.10 ... 64 bytes from 10.50.4.10: icmp_seq=1 ttl=61
2 packets transmitted, 2 received, 0% packet loss
OPEN

Verificación: ruta principal desaparece, ruta flotante (via 10.10.12.2 eth1) asume el tráfico; ping y web siguen funcionando 0% loss = failover automático exitoso.

Error típico: failover no ocurre = AD flotante no mayor que principal, o ruta flotante mal escrita. Corrección: AD flotante > AD principal (10 > 1).

Verificador: criterio de redundancia y failover.
